### Warnings

#### `onClose`'s synchronous archive mirror can stall session-scope release for an unbounded time
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionArchiveHook.scala:60-61` (interacting with `zio/src/works/iterative/claude/zio/internal/cli/SessionProcess.scala:74` and `:291-318`)
**Problem:** The reader is started with `.forkScoped` (`SessionProcess.scala:63-74`). `forkScoped` registers a finalizer that *awaits the fiber's interruption* when the enclosing `Scope` closes. The reader's terminal step, `recordEnd`, calls `archiveHook.onClose(id)` (`SessionProcess.scala:313-315`) *before* shutting down `eventsHub`/`stateChangesHub`, and `onClose` is deliberately synchronous: `permit.withPermit(mirror(sessionId))` (`SessionArchiveHook.scala:60-61`) blocks until any in-flight `afterResult` mirror finishes and then runs the final mirror itself — a blocking, `ZIO.attemptBlocking`-wrapped filesystem tree copy (`ZioConversationArchive.scala:60-67`, `83-113`).
**Impact:** When a caller releases the session's `Scope` (e.g. the `ZIO.scoped` block around `ClaudeCode.session` exits) — whether because the process died naturally or the caller is tearing down early — release now waits for this archive copy to complete. `ZIO.attemptBlocking` effects are not reliably preemptible mid-flight: the runtime can request interruption, but a thread blocked in synchronous file IO (`os.copy`, `os.read.bytes`, `os.write.append`) generally will not observe it until the blocking call itself returns. For a large or slow vendor tree, this turns `Scope` release — which callers reasonably expect to be prompt once `process.killForcibly` has run — into an operation with no effective upper bound. None of the current tests exercise this path with a nontrivial tree size (`SessionIntegrationTest`'s archive test uses an empty directory, so the mirror is a no-op), so the regression would not show up in CI.
**Recommendation:** Either (a) give `onClose`'s mirror a bounded `timeout` (matching the existing `InterruptTimeout` pattern already used for `interrupt`), logging and moving on if it doesn't finish in time, or (b) explicitly document on `ClaudeCode.session`/`Session` that releasing the scope can block for the duration of the final archive mirror when `archive` is configured, so callers can choose to fork the release themselves. Also worth revisiting whether `Session.events`/`Session.stateChanges`'s doc claim "completes when the session's process ends" still holds when archiving is on — today, hub shutdown is gated on the same synchronous `onClose` call.

```scala
// SessionArchiveHook.scala — bound the final mirror instead of an unbounded wait
def onClose(sessionId: String): UIO[Unit] =
  permit.withPermit(mirror(sessionId))
    .timeout(SomeConfiguredArchiveTimeout)
    .unit
```

#### Fixed `ZIO.sleep` used to synchronize test fiber startup instead of a deterministic signal
**Location:** `zio/itest/src/works/iterative/claude/zio/SessionIntegrationTest.scala:138-141`
**Problem:** `"two events subscribers both see the same messages"` forks two `events.filter(...).runCollect` consumers and then does `_ <- ZIO.sleep(200.millis) // both subscriptions active before send` before calling `session.send`. `ZStream.fromHub(eventsHub)` subscribes asynchronously inside the stream's own pull, so there's no guarantee the 200ms is enough on a loaded CI box — this is exactly the kind of scheduling assumption the ZIO idiom (`fiber.status.repeatUntil(_.isSuspended)`, used correctly a few lines above in the same file at `SessionTest.scala:152,163,191`) exists to avoid.
**Impact:** Flaky test under load; a slow-to-subscribe fiber can miss the early messages the assertion depends on, causing an intermittent, hard-to-reproduce failure.
**Recommendation:** Poll on fiber suspension the same way the unit test rig does, or have the two forked collectors signal a `Promise` once each has begun pulling before the test proceeds to `send`.

### Suggestions

#### Test fixtures use `ZIO.attempt` for filesystem setup instead of `ZIO.attemptBlocking`
**Location:** `zio/test/src/works/iterative/claude/zio/log/ZioConversationArchiveTest.scala:39-54` and its several inline `ZIO.attempt(os.write/os.read/...)` calls (e.g. `:133-139`, `:186-188`, `:213-215`, `:230-235`, `:248-249`, `:264-270`, `:291-297`)
**Problem:** These are synchronous, potentially slow filesystem calls (`os.temp.dir()`, `os.write`, `os.read.bytes`) run via `ZIO.attempt`, which executes on the regular fiber-runtime executor rather than the dedicated blocking pool.
**Impact:** Minor in a test suite (small files, short-lived), but it's the same pattern flagged as an anti-pattern in production code, and normalizing it in tests risks it being copied into production paths later.
**Recommendation:** Use `ZIO.attemptBlocking` for consistency with the production `ZioConversationArchive` code (which correctly uses `attemptBlocking` for `forSession`/`mirror`).

#### Per-result archive hook forks a fresh daemon fiber even when a mirror is already running
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionArchiveHook.scala:58-59`
**Problem:** `afterResult` unconditionally does `permit.tryWithPermit(mirror(sessionId)).forkDaemon`, so a burst of results in quick succession forks one daemon fiber per result even though `tryWithPermit` will immediately return `None` for all but the one holding the permit.
**Impact:** Negligible at typical result rates, but it is needless fiber churn under a high-frequency result stream (e.g. many background task notifications).
**Recommendation:** Not worth a design change given the low expected frequency of real results per session — noting only as a minor efficiency observation, no action needed unless result frequency turns out to be much higher than expected.

#### `pendingRequests` registry logic scattered across the file instead of owning its own small type
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionProcess.scala:249` (`routeControlResponse` — complete-and-remove), `:320` (`failPendingRequests` — drain-and-fail-all), `:392-420` (`SessionImpl.interrupt` — register, re-check-liveness, remove-on-timeout)
**Problem:** Three different call sites each reach directly into the raw `Ref[Map[String, Promise[CLIError, ControlResponse]]]` and perform their own `.update`/`.modify`/`.getAndSet` on it, duplicating the map-manipulation idiom (`_.update(_ + ...)`, `_.update(_ - ...)`, `.getAndSet(Map.empty)`).
**Impact:** Not a bug today, but the registry's invariants (a request id is registered exactly once, removed exactly once, and always resolved on shutdown) live only in the heads of whoever wrote each call site rather than in one place that can be tested and reused.
**Recommendation:** Extract a tiny `PendingRequests` wrapper around the `Ref` with `register`, `complete`, `remove`, and `failAll` operations, and use it at all three sites. This is optional polish, not a blocking concern, since the current code is still correct and each site is well-commented.
```scala
private final class PendingRequests(ref: Ref[Map[String, Promise[CLIError, ControlResponse]]]):
  def register(id: String, p: Promise[CLIError, ControlResponse]): UIO[Unit] = ref.update(_ + (id -> p))
  def remove(id: String): UIO[Unit] = ref.update(_ - id)
  def complete(response: ControlResponse): UIO[Unit] =
    ref.modify(m => (m.get(response.requestId), m - response.requestId))
      .flatMap(_.fold(ZIO.unit)(_.succeed(response).unit))
  def failAll(error: CLIError): UIO[Unit] =
    ref.getAndSet(Map.empty).flatMap(m => ZIO.foreachDiscard(m.values)(_.fail(error)))
```

#### `afterResult` test polls a real background fiber for filesystem side effects instead of asserting deterministically
**Location:** `zio/test/src/works/iterative/claude/zio/internal/cli/SessionArchiveHookTest.scala:31-45`

## Security Review

### Critical Issues

#### Path Traversal via Unvalidated `sessionId` in Archive Path Resolution
**Location:** `core/src/works/iterative/claude/core/log/ArchivePaths.scala:16-21` (built), consumed unchecked by every entry point in `zio/src/works/iterative/claude/zio/log/ZioConversationArchive.scala:33-43,60-67,115-121` and declared with no trust caveat in `core/src/works/iterative/claude/core/log/ConversationArchive.scala:30-43`

**Problem:** `mainTranscript`/`treeDir` build paths with `projectDir(config) / s"$sessionId.jsonl"` and `projectDir(config) / sessionId`. `os.Path`'s `/` operator (os-lib `PathChunk`) splits the string on `/` and resolves `..` segments — I verified this directly:
```
os.Path("/tmp/base") / "../../etc/passwd"  →  /etc/passwd
```
`sessionId` is a bare `String` parameter on the public `ConversationArchive[F]` trait (`forSession`, `entries`, `subagentEntries`, `mirror`) and is never validated anywhere in the call chain — not in `ArchivePaths`, not in `ZioConversationArchive`, not in `ArchiveConfig`. Nothing restricts it to the vendor's actual id format (a UUID/opaque token).

**Impact:** Any caller of the public API (a host application exposing "show me session `<id>`" to a user, or any code path that threads an externally-influenced identifier into `sessionId`) can pass a value like `"../../../../home/victim/.ssh"` and:
- `forSession`/`entries` will read whatever file happens to sit at the traversed path (gated only by requiring a same-named `.jsonl` file to exist for the initial existence check).
- `mirror(sessionId)` is worse: `treeDir` has no filename suffix constraint at all, so a traversed `treeDir` pointing at an arbitrary directory gets `os.walk`ed (`sourceFiles`, line 115-120) and every file under it is `os.copy.over`'d (line 136-137) into `config.archiveDir` — i.e. an attacker-chosen directory's contents can be exfiltrated into the archive.

This is exactly the defect class the review context flagged, and it is present with no mitigation.

**Recommendation:** Validate `sessionId` (and, defensively, `parentToolUseId`) at the boundary before it ever reaches path construction — reject anything containing `/`, `\`, or `..`, or better, allow-list to the vendor's actual id shape (e.g. `^[A-Za-z0-9_-]+$`). Centralize the check in `ArchivePaths` so every path derived from `sessionId` is forced through it, failing with a typed `ArchiveError` (e.g. `InvalidSessionId`) rather than silently building a traversed path:

```scala
// ArchivePaths.scala
private val ValidId = "^[A-Za-z0-9_-]+$".r

def mainTranscript(config: ArchiveConfig, sessionId: String): Either[ArchiveError, os.Path] =
  requireValidId(sessionId).map(id => projectDir(config) / s"$id.jsonl")

private def requireValidId(id: String): Either[ArchiveError, String] =
  Either.cond(ValidId.matches(id), id, InvalidSessionId(id))
```

### Warnings

#### Mirror Follows Symlinks, Enabling Arbitrary File Content to Be Copied Into the Archive
**Location:** `zio/src/works/iterative/claude/zio/log/ZioConversationArchive.scala:115-120` (`sourceFiles`), `136-137` (`copyWhole`); planning logic in `core/src/works/iterative/claude/core/log/MirrorPlanner.scala`

**Problem:** `sourceFiles` lists the tree with `os.walk(record.treeDir).filter(os.isFile)`. I verified `os.isFile` follows symlinks by default — a symlink pointing at `/etc/hostname` is reported as a regular "file" by the walk (`os.isLink` on the walked entry is `true`). `copyWhole` then calls `os.copy.over(source, dest, createFolders = true)`, which I verified dereferences the symlink and copies the *target's* actual bytes, not the link itself. Nothing in `MirrorPlanner` or `ZioConversationArchive` excludes symlinks from the source listing.

**Impact:** If anything is ever able to place a symlink inside the vendor session tree that this process can read (a bug in the vendor CLI, a shared/writable projects directory, another process on the same account), `mirror()` will silently copy the symlink target's content into `config.archiveDir` regardless of what it points to — defeating the intent of treating the archive as a faithful, bounded copy of only the session's own records.

**Recommendation:** Exclude symlinks from the source listing explicitly (`os.isFile(p, followLinks = false)` or filter `!os.isLink(p)`), or if symlinks are expected to occur legitimately in vendor trees, copy them as symlinks rather than dereferencing.

#### Verbatim User Input Logged at DEBUG
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionProcess.scala:388-389`

```scala
val line = SessionStdin.userInputLine(input, idOpt.getOrElse(""))
ZIO.logDebug(s"Writing user input to stdin: ${line.trim}")
```

**Problem:** This logs the entire stdin line — the full JSON-encoded `UserInput` including the verbatim user text and all context blocks — at DEBUG level. Per the security skill's Logging Security checklist ("No passwords, tokens, or secrets in logs", "Sensitive data masked in debug logs"), and per the review context's own concern ("no secrets should be logged"), this is exactly the kind of statement that turns a routine debug session into a PII/secret leak: users frequently paste credentials, tokens, or personal data into these messages, and DEBUG logging is commonly enabled during troubleshooting in exactly the situations where sensitive content is most likely to be present.

**Recommendation:** Log a redacted/structural summary instead of the raw content, e.g. block count and channel, not the text itself:
```scala
ZIO.logDebug(s"Writing user input to stdin (${blocksCount} blocks, channel=${input.channel})")
```

#### Mirror-Created Directories Get Default (umask) Permissions While Vendor Files Are 600
**Location:** `zio/src/works/iterative/claude/zio/log/ZioConversationArchive.scala:136-137` (`copyWhole` with `createFolders = true`)

**Problem:** I verified `os.copy.over(source, dest, createFolders = true)` preserves the source file's permission bits (a 600 source file copies to a 600 destination — good), but any *directories* it creates along the way get the process's default umask-derived permissions (verified `rwxrwxr-x` under this environment's umask), not restricted to the owner. The review context explicitly notes vendor transcripts are `chmod 600`; the mirror partially honors that intent for files but not for the containing directory tree.

**Impact:** Directory listings under `config.archiveDir` (session ids, sub-agent tree structure, filenames) are readable by other local users/groups even though file contents remain protected. Low severity given file content stays 600, but it's an inconsistency with the apparent hardening intent and leaks structural metadata.

**Recommendation:** After `os.copy.over`/`os.makeDir.all` creates the archive directory tree, explicitly set restrictive permissions (e.g. `700`) on `config.archiveDir` and any directories created under it, or create them up front with `os.makeDir.all(dir, os.PermSet(0700))` before mirroring into them.

## Error Handling Review

### Critical Issues

None found.

The new error surfaces are well-designed: `ArchiveError`/`CLIError` are proper sealed hierarchies extending `Throwable` only so they can terminate a `Throwable`-shaped stream/IO at the boundary, while the actual effect signatures throughout (`IO[ArchiveError, A]`, `IO[CLIError, A]`) keep the error channel typed rather than falling back to `Task`/generic `Throwable`. No `throw` in business logic, no `Task[_]`/`RIO[_]` leaking into the public API, `UserInput.decode` returning `Option` is a defensible absence-vs-error choice (it documents precisely which inputs are `None` and why), and `SessionArchiveHook`'s catch-and-log-swallow for *whole-mirror* failures is an explicit, tested, documented decision appropriate for a best-effort side channel.

### Warnings

#### Reader-stream failures swallowed without logging
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionProcess.scala:177` and `zio/src/works/iterative/claude/zio/internal/cli/SessionProcess.scala:334`
**Problem:** `startReader`'s `.runDrain.catchAll(_ => ZIO.unit)` and `captureStderr`'s `.catchAll(_ => ZIO.unit)` both discard the underlying `Throwable` from `process.stdout.linesStream` / `process.stderr.linesStream` with no log statement at all. Every other failure path in this file (`JsonParser` parse errors, mirror failures) is logged before being swallowed; these two are not.
**Impact:** If the stdout/stderr pipe fails for a genuine I/O reason (not just normal process-exit EOF), the reader silently stops and `recordEnd` reports only the exit code — the actual cause of a broken read is invisible to anyone debugging a session that ended strangely. This is exactly the "recovery without logging" anti-pattern the skill flags.
**Recommendation:** Log the cause before swallowing, mirroring the pattern already used for malformed JSON lines:
```scala
.runDrain
.catchAll(cause => ZIO.logWarning(s"Session reader stream failed: $cause"))
```
and similarly for `captureStderr`.

#### Per-file mirror failures captured but never surfaced
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionArchiveHook.scala:50-57`, `zio/src/works/iterative/claude/zio/log/ZioConversationArchive.scala:88-113`
**Problem:** `ZioConversationArchive.runMirror`'s `guarded` helper is careful to capture individual copy/extend/recopy failures into `MirrorReport.failed` rather than throwing (good — that's the intended self-healing/idempotent-retry design per `MirrorReport`'s own doc comment). But `SessionArchiveHook.mirroring`'s `mirror` function calls `archive.mirror(sessionId).unit`, discarding the successfully-returned `MirrorReport` entirely — including any non-empty `failed` list. The hook's doc comment claims "A mirror failure is logged as a warning and swallowed," but that only holds when the *whole* `mirror` IO fails (e.g. `SessionNotFound`); a partial, per-file failure inside a successful report is never logged, and `SessionArchiveHookTest` only exercises the whole-failure case.
**Impact:** A file that persistently fails to copy (e.g. permission error, disk full) produces zero observable signal — not even a debug log — every single time the hook runs, silently contradicting the documented "mirror failure is logged" contract.
**Recommendation:** Log when `report.failed` is non-empty in `SessionArchiveHook.mirror`:
```scala
def mirror(sessionId: String): UIO[Unit] =
  archive.mirror(sessionId).flatMap { report =>
    ZIO.when(report.failed.nonEmpty)(
      ZIO.logWarning(
        s"Session archive mirror for '$sessionId' had ${report.failed.size} failed file(s): ${report.failed.map(_._1).mkString(", ")}"
      )
    )
  }.catchAll(error => ZIO.logWarning(s"Session archive mirror failed for '$sessionId': ${error.message}"))
```

#### `SessionProcessDied` constructed with a permanently empty `stderr` and a misleading message on clean exit
**Location:** `zio/src/works/iterative/claude/zio/internal/cli/SessionProcess.scala:307` and `:328`
**Problem:** Both places that build a `SessionProcessDied` in `recordEnd`/`failPendingRequests` hardcode `stderr = ""`, even though `captureStderr` (line 331-334) is reading the real stderr lines concurrently — that content is only sent to `ZIO.logDebug` and never threaded into the death error. Separately, `failPendingRequests`'s fallback `error.getOrElse(SessionProcessDied(exitCode, ""))` fires whenever a control request is pending at process end — including a clean exit (code 0, where `recordEnd`'s own `error` is `None`) — producing the message "Session process exited unexpectedly with code 0," which is factually wrong for a clean shutdown.
**Impact:** Callers catching `CLIError` for a died interrupt/send get an error type whose `stderr` field is defined in the ADT but never populated, and — in the clean-exit-with-pending-request race — a message that claims an unexpected death that did not occur, reducing trust in the error text.
**Recommendation:** Accumulate the last N stderr lines (or at least the last line) into a `Ref[String]` alongside `captureStderr`, and thread it into both `SessionProcessDied` constructions; for the clean-exit-with-pending-request case, consider a distinct message/case (e.g. "session closed before this request completed") rather than reusing "exited unexpectedly."

### Suggestions

#### `ArchiveError` flattens domain and technical concerns into one sealed trait
**Location:** `core/src/works/iterative/claude/core/log/ArchiveError.scala:10-30`
**Problem:** `SessionNotFound`/`SubAgentNotFound` (expected, domain-level "not found") and `ArchiveIOError` (technical, wraps an arbitrary `Throwable` cause) sit as flat, undifferentiated siblings under `ArchiveError`.
**Impact:** Minor — for a bounded, 3-case port error this is easy to pattern-match correctly today, but it doesn't scale if more technical failure modes get added later, and it's inconsistent with the domain/technical split the skill (and `CLIError`, which has a similar but larger flat list) generally recommends.
**Recommendation:** If this hierarchy grows, consider splitting into `ArchiveError.NotFound` (domain) and `ArchiveError.IOFailure` (technical) sub-traits. Not worth doing now for 3 cases.

**Location:** `zio/src/works/iterative/claude/zio/log/ZioConversationArchive.scala:163-164`
**Problem:** `toArchiveError`'s catch-all wraps unmapped throwables as `ArchiveIOError(Option(other.getMessage).getOrElse(""), other)`, using an empty string when `getMessage` is `null` — unlike `failureMessage` a few lines above (`:157-158`), which falls back to `cause.toString` (which at least names the exception class).

#### `os.Path`/`os.SubPath` in the port signature — deliberate, not leakage

#### Interface bundles "read" and "mirror" concerns; two of four port methods are exercised only by tests
**Location:** `core/src/works/iterative/claude/core/log/ConversationArchive.scala:24-44`; production caller `zio/src/works/iterative/claude/zio/internal/cli/SessionArchiveHook.scala:49-52`
**Problem:** `ConversationArchive` bundles four responsibilities — locate (`forSession`), read main-thread entries (`entries`), read sub-agent entries (`subagentEntries`), and custody sync (`mirror`) — into one port. The only production caller today (`SessionArchiveHook.mirroring`) calls `archive.mirror(sessionId)` alone; `forSession`, `entries`, and `subagentEntries` currently have no production callers (`rg` for `.entries(` / `.subagentEntries(` / `.forSession(` outside test trees returns nothing).
**Impact:** From an interface-segregation standpoint, a consumer that only wants "keep the archive current" doesn't need the read-side methods on the interface it's coupled to. **Mitigating context:** ADR 0001 explicitly flags this itself under "What this ADR does NOT settle": *"`ConversationArchive`'s signatures... **Recommendation:** When the ADR's open question is revisited, consider whether "locate + read" (query side) and "mirror" (custody/write side) want to be two smaller ports rather than one, especially once a second production consumer of the read side appears (per the codebase's own YAGNI stance, this can legitimately wait until then).

**Impact:** This is adapter-to-adapter coupling that bypasses the `ConversationLogIndex` port abstraction entirely (it depends on the concrete `ZioConversationLogIndex` class, not the trait), and it duplicates config-shape parameters that don't apply to this call path. It's not incorrect — `listSubAgents(projectPath, sessionId)` genuinely ignores `configDirOverride`/`home` — but the dead parameters at the call site are a minor readability/maintenance smell: a future reader has to go check `ZioConversationLogIndex` to confirm the comment's claim still holds.
